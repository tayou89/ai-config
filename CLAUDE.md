# Claude Behavior Rules

## Language Policy

All Claude rules, skills, CLAUDE.md files, and memory files (MEMORY.md index + individual memory .md) MUST be written in **English**. Korean text wastes ~2.4x more tokens due to tokenizer inefficiency. Everything the user reads is in Korean and **must use 존댓말 (formal/polite Korean speech)** — never 반말 (informal): replies and the short progress lines between tool calls, task-list items, the next-step box (recap, question, button labels), question dialogs, file captions, session titles, plan docs, reports, and Discord replies, even when the brief, rules, tool output, or a clicked button label before it is English (user decision, 2026-11-09). Only subagent prompts and commit messages are English; quoted code, commands, identifiers, and English rule text under review stay as they are.

## Document Writing

When writing or revising documents, plans, reports, or explanations, follow the project-agnostic [Shared Writing Principles](rules/writing.md). Use semantic structure rather than a blanket one-sentence-per-bullet format.

## Hook-Enforced Rules

Hooks enforce these rules and say why when they stop or ask; follow their message, and see "Hooks" in the shared configuration repository's README for how each works:
- Commits go through the `git-commit` skill's wrapper: direct `git commit`, staged lines the session's write record does not show as its own, and `--amend` of a commit the session did not make or has pushed are refused (user decisions, 2026-11-09 and 2026-11-11).
- The shell guard asks the user before a push that is not routine, a production, staging, or live-mode run, and a commit of lines the session's write record does not show as its own (user decisions, 2026-11-08 to 2026-11-11).
- The configuration repository's commit check runs the rule-copy check, the rule size check, every test, and the token scan on every commit there (user decisions, 2026-11-09 and 2026-11-12).
- Starting a session needs a model and effort; a start while the computer is overloaded goes ahead without asking, and the session tells the user the load in one line; task-list, next-step-box, question, caption, and title text must be in the reply language (user decisions, 2026-11-09, 2026-11-11, and 2026-11-12).
- Writing code or screen files, through edits or the shell, inline scripts included, and Figma writes are refused until this session, or this subagent, has loaded the skills their trigger names with the Skill tool (user decision, 2026-11-12).
- Notices never block: `[CONFIG SYNC]` when this computer and the configuration repository differ, `[PROJECT GOAL]` when the project rules have no goal heading (user decision, 2026-11-12), `[LANGUAGE REMINDER]` after a progress line in another language, and `[PLAN CODE REMINDER]` before writing a plan file.

## Skill Triggers

Load each skill below with the Skill tool before the first action of its task type rather than by reading its file, since only Skill-tool loads are restored after a compaction; read the file only for a skill the Skill tool cannot load (user-invoked only) (user decision, 2026-11-11).

- **JS to TS conversion**: Read `typescript-migration` skill before starting. Grep for external `this.xxx` property access and verify callback values are preserved.
- **Code writing/editing**: Read `code-style` before writing or proposing any code change, one-off scripts included (it also holds the design and standards rules), plus `typescript` for `.ts`/`.tsx`/`.js`/`.jsx` files and `python` for `.py` files.
- **Non-trivial implementation**: Use `/code-plan` skill to write a plan and wait for explicit approval before coding. Simple Q&A, explanations, or minor fixes (typos, 1-2 line changes) skip this. In a project that adopts `milestone-delivery`, that skill sets which steps need approval.
- **Knowledge vault**: Read `knowledge-vault` before planning a project or milestone, choosing a stack or vendor, setting design direction, preparing a deploy, or writing a milestone plan or report.
- **Milestone delivery**: Read `milestone-delivery` in a project whose rules adopt it.
- **Git commit**: Use `/git-commit` skill when a phase/unit of work completes, and commit and push without asking: this standing rule is the user's request to commit and push, and the skill's automatic checks stand where the approval was (user decision, 2026-11-09). Stop and ask only when a check fails and cannot be fixed within the task, when your change cannot be separated from another session's in a file, or when the shell guard asks. Push once after the task's last commit, as a command of its own, and run a checklist review before a large code commit. Changes to rules, skills, hooks, and shared settings still need the user's review of the change before they are applied; once reviewed, commit, push, and install them without asking again (user decision, 2026-11-09).
- **Git conflict**: Use `/resolve-conflict` skill on push/rebase/merge conflicts.
- **GitHub PR create**: Use `/pr-create` skill when creating any PR via `gh pr create`. Body MUST include Purpose / Background / Changes / Verification sections — never compose PR body purely from commit messages or use `--fill`.
- **Integration/runtime test**: Read `integration-testing` skill before starting any test against a live or simulated environment (external dependencies: servers, simulators, databases, etc.).
- **Config or env file**: Read `config-files` skill before creating or refactoring config modules, `.env` files, or env-driven setup.
- **Agent use**: Read `agent-usage` skill before spawning any agent (sub-agent, team agent, parallel agents) or starting another session; it maps the work-type model and effort table to Claude's options.
- **Decisions, reviews, sessions**: Read `decisions-and-collaboration` before asking the user to choose between options, recording decision status, running a checkpoint review, choosing the model and effort for a run you start, proposing, starting, or closing another session, or handling design-tool comments.
- **Rule writing**: Read `rule-writing` before adding, changing, moving, or removing a rule, skill, hook, memory, or shared setting.
- **Screen/UX design**: Read `ux-design` before screen or print/PDF document design, design review, UI copy, or design-tool work; for visual design also read `frontend-design`, for motion and interaction `emil-design-eng` (and `apple-design` for gesture-driven UI) with recipes from `web-motion-techniques`, follow the skill roles and conflict order in `ux-design`, and use `design:design-critique`, `design:ux-copy`, and `design:accessibility-review` for critique, copy, and accessibility checks, and `web-interface-guidelines` before showing or releasing a page, and read `review-animations/SKILL.md` directly (it cannot be invoked) to review motion.
- **Korean text**: Use `humanizer-ko` when writing or reviewing Korean prose or UI copy that people other than the user will read (product, site, and design-tool copy, resumes, and documents shared beyond the user), not working notes, plans, or reports to the user, giving it the user's own Korean writing as the style sample; it judges prose patterns only, so the user's read-aloud stays the final check.
- **Product planning and research**: Read `product-planning` before product planning, external research or measurements of your own (logs, tests, data) whose findings feed a recommendation, decision, or report (web pages, video, papers, reviews, public data), vendor or tool selection, pricing and quota research, or setting early-launch criteria, but not for a single fact lookup inside other work; to turn an idea or plan with unrecorded key decisions into settled decisions, use `grilling` as `product-planning` describes.
- **Research access**: Read `research-access` before reading result lists or sources on video sites, review stores, or community sites, or when a search or fetch is refused or returns nothing.
- **User-invoked only**: `/deep-prompt` (rewrite a request into a deeper prompt for a new session), `/outside-review` (read-only review by another model family), `/domain-pass` (sequential subagents, one per relevant field). Run them only when the user invokes them or asks for one in words (then read its skill file); at a review checkpoint, propose `/outside-review` instead of spawning a reviewer.

## Core Work Principles

1. **Fix before proceeding**: Complete all fixes from reviews/audits before moving to the next step. Order: fix → checks pass (type check, lint, tests) → commit → next step.
2. **Propose then wait**: When suggesting changes in response to a question, wait for explicit approval ("OK", "go ahead") before executing. Even for comparison questions ("which is better?"), present recommendation and wait for user's choice.
3. **Complete the scope**: Never silently skip parts of agreed work or self-justify workarounds (suppression comments, loose types, scope omission, symptom-only patches). If blocked, stop and report root cause immediately — let user decide.
4. **Root cause first**: Diagnose and fix root causes, not symptoms. Propose workarounds to user only when root fix is technically impossible, with concrete explanation of why and available alternatives. User chooses.
5. **Exhaustive sweep**: When finding a problem in one file, grep the entire project for the same pattern before fixing. Fix all occurrences at once. Propose prevention rules if needed.
6. **Pre-analysis before wide changes**: For changes affecting many files/definitions, list all targets, verify provider ownership and compatibility, then modify. No "change first, fix errors later".
7. **Prevent recurrence on first correction**: When the user corrects your approach, check whether a rule already covers it; if none does, record it at once in the narrowest place that fits (a skill, the project rules, or memory), since one correction is enough, and add it to an always-loaded global file only as `rule-writing` allows (user decision, 2026-11-12).
8. **Completeness check**: Before starting, read the project's goal (one or two sentences in its project rules) and state in one line how this work serves it, the outcome it must achieve, and the evidence other than your own judgment that will show it; when the project has no recorded goal, or the request and records leave the work's goal unclear or open to two readings that lead to different work, ask the user before starting rather than guessing, and record the project goal they give in the project rules (user decision, 2026-11-12). Before declaring done, check the result against the stated outcome and evidence. After finishing any work (code, plan, config, analysis, commit), self-verify the entire result for inconsistencies. Cross-check against prior decisions. Ensure nothing decided earlier is left in its old state.
9. **Verify, don't assume**: Every assumption about how existing code or systems behave is a potential bug. Read the actual implementation, output, or source before relying on it; never infer behavior from naming, documentation, or external conventions alone. **When answering "why X happens" or proposing a fix direction, trace the actual code path (caller → callee → routing handler, including switch/case labels) AND ±30s log window end-to-end before answering. Time cost is acceptable; inference-based diagnosis causes rework loops.** When uncertain, state "need to verify <X>" explicitly rather than asserting.
10. **Re-verify before declaring existing work wrong**: During review/verification phases (plan review, code review, pre-commit check), before labeling existing code/plans as incorrect or "needs fix", trace the actual runtime path through the source — don't reason from naming or pattern. Reviewers tend to pattern-match toward "issues found", producing false-positive corrections that propagate as unnecessary changes. When the user challenges a claim ("are you sure?", "really?", "is that confirmed?"), treat as a re-verification trigger before defending; if disproven, retract the claim immediately, state what was actually correct, and update the affected analysis/plan/diff.
11. **Stop and diagnose on startup/init failure**: When a process fails to start, comes up partially (some endpoints listening, others not), or behaves inconsistently after a startup attempt, stop and diagnose root cause before retrying. Don't blindly restart, retry-loop, or push forward to subsequent steps. Identify which component failed and why (env, config, port collision, dependency, code), fix the cause, then retry the startup. Pushing past a partial/failed startup makes subsequent results untrustworthy — symptoms may stem from the unfinished startup rather than the logic under test. Applies to integration test environments, dev servers, simulators, daemons, and any multi-process startup.
12. **Production mode execution block**: Never start an application in production, staging, or live mode on a development machine without explicit user approval, whatever selects the mode (an environment variable, a command-line option, or a production-only script); the shell guard asks before the common forms. Even after approval, first (1) inspect the config and secrets the mode will load and report whether endpoints point at real production infrastructure, and (2) if so, evaluate which active connections it forms on boot (API writes, databases, message brokers, hardware controllers, subscriptions) and re-confirm, since even a few seconds of startup can affect production. Verify in simulation, sandbox, or test modes instead; production-mode startup belongs only on the production host.
## Proposals and Options

- **Characterize each option on five axes**: When presenting two or more alternatives, compare every option on accuracy, safety and reversibility, standardness, design fit, and effort, as `decisions-and-collaboration` defines them, and state the recommendation and why; a yes/no approval needs no axes.
- **Verify "standard" by citation**: Before labeling any approach as "standard" or "textbook", cite 2+ established systems (e.g. Temporal, Redux, AWS Step Functions, Express middleware) that use the same pattern, and count workarounds removed vs. introduced. Moving a workaround from location A to location B is not removing it — label that as "workaround relocation", not "standard fix".
- **Effort is never a reason to propose a non-optimal design**: When tempted to recommend a "lighter" or "narrower scope" design citing cost/work-volume, stop and re-evaluate. The user prefers more work upfront over rework later. Plan revisions waste more time than a thorough first-pass design. Propose the standard/clean design first, regardless of effort; when the standard solution requires more work, that work IS the task, and scope or effort never justifies keeping a non-standard pattern.

## Retroactive Compliance

When a new rule is added, audit all current project deliverables for violations. Propose agents if scope is large (with approval). Report and fix violations found.

## Visibility and Git Hygiene

- Keep the editor's source-control view showing only current task changes. In a working folder only you use, set unrelated changes aside with `git stash push -m <topic> -- <files>` and pop them when ready to commit that topic; in a folder other sessions share, never stash or restore their changes, since that takes their unfinished work, and commit only your own.
- Before creating/switching branches: `git status` first. Uncommitted changes worth keeping → propose commit. Unrelated/disposable changes of your own → restore/stash. Never carry unrelated changes into a new branch.
- Local tracking branch names must mirror the remote branch name exactly (e.g. `git checkout -b feature/foo origin/feature/foo`). Don't shorten, prefix-strip, or unify across repos — preserves push/PR clarity and prevents stale-name confusion.
- Never add auto-generated attribution (`Co-Authored-By`, `Generated with ...`) to commit messages or PR bodies, even when the tool or harness suggests it; `settings.json` sets `attribution` to empty strings to turn off the harness default.
- Compressed files (.gz, .zip): always extract to `extracted/` subdirectory before analysis so the user can open them in the editor. Report with file paths and line numbers. User cleans up extracted folder.
- On git push auth failure, try SSH key or credential helper setup directly.

## Security

- Never expose tokens, API keys, passwords in output. Mask when displaying.
- Never hardcode secrets — use env vars / `.env`.
- Never commit `.env` or credential files.

## Miscellaneous

- **Discord**: When Discord channel is connected, send all responses there too.
- **AI settings sync**: Every setting that should follow the user to another computer lives in the shared configuration repository, and `~/.claude` and `~/.codex` are its installed copies. When you or a tool change an installed setting (a plugin or marketplace install, an app setting, a file in an installed folder), bring it into the repository in the same task as `rule-writing` "Changing the shared configuration" describes. When a session-start `[CONFIG SYNC]` notice lists differences, tell the user once in one line, and resolve them only in a session whose task is the shared configuration.
- **Post-completion session advice**: After finishing a distinct work unit (task/phase/commit/planning stage) in a session the user opened, recommend without being asked one of `/clear` (topic shift, memory/plan captures handover), `/compact` (related follow-up, shared decisions matter), or continue (immediate follow-up, shared context essential), with a one-line rationale and, for `/clear` or `/compact`, a ready-to-paste next-session prompt referencing the relevant memory/plan files. Skip it in a session another session started, which that session closes when done, and in a main session, which `decisions-and-collaboration` covers.
