# Session Management Principles

Apply in every project when proposing, starting, messaging, running, or closing other sessions, as a main session or for one, and before taking on work outside your session's area. Choose each run's model and effort from the work-type table in `decisions-and-collaboration`. The principles every task needs are in `collaboration-core.md`. These generalize feedback the user gave repeatedly during project work. Follow project rules first.

## Working alongside other sessions

- Do not touch comparison boards, decisions, or screens made by other sessions. If two sessions must edit the same screen, ask the user which one takes it.
- Before a task writes in a repository whose rules use worktrees, give it its own worktree, branch, starting commit, and the runtime resources it needs (ports, databases), whoever starts it: the user, a session, a scheduled run, or another tool. A resident coordinating session only reads in the original checkout and routes file changes to a writing task; when isolation cannot be set up, the task does read-only work and reports what is missing (user decision, 2026-11-13).
- Give work that finishes on its own a new session: it leaves its own result (e.g., implementing another page or researching another topic), and the decisions it needs are already recorded, so a short brief is enough to start it. Keep in the current session work that carries out what was just decided or that needs context found only in the conversation.
- Prefer a new session for such work even more when the current conversation is already long or has been summarized, even when a few tool calls would do it: carrying the whole history costs more every turn and summaries lose detail, while a new session re-reads only the recorded decisions it needs.
- Start such a session without asking, in a main session or not, and tell the user in one line what it takes on, which files it changes, and what it leaves when done; do not offer a card asking whether to do it here instead (user decision, 2026-11-13). When it would edit files another session is editing, hand it to that session or agree the order with the user instead. Where the tool allows only a proposal, as on a turn another session's message started or for work you noticed that the user did not ask for, propose it with the same content and no separate question.
- Keep each session to one area, the topic its title and brief name or the role its project rules give it; a main session's area is managing the sessions under it (user decisions, 2026-11-13). Work the title would no longer describe does not join the session, even when it follows from what was just done there. Before starting a session for any work, a main session's follow-ups included, look for a session that already owns that area or holds its context, by title in the session list without archived ones and in the shared notes index: rules, skills, hooks, and AI settings belong to the session titled “Claude 설정 관리”, and a project's rules name its role sessions by title in a list under a "Role sessions" heading, one item per role starting with its title in backticks; `(not main)` right after a title marks a top-level role the user set apart from the main session, and the main-session notice reads that mark (user decision, 2026-11-16). When one exists, hand the work to it, ask its opinion, or ask it to review your result, and start a new session only when it asks to split the work off or its context is past 80% or summarized; when none exists, start one as above. Outside your area, do only what a handful of tool calls settles without changing anything, such as reading a file or checking a status.
- When you hand work to another session or ask it for an opinion or a review, send what to look at as paths (naming any that still hold your uncommitted changes, with your session's id, so the receiver can take them over), the decision it bears on, when it is needed and what it blocks, and the user's words quoted with their date and session, and tell the user in one line where it went; the reply gives agreement, disagreement, or an alternative in a few lines with reasons (user decision, 2026-11-13). When the two sessions disagree, show the user both views side by side with your recommendation.
- Announce a change other sessions need, such as a changed rule or a fixed shared tool, as one line in `~/Library/Application Support/Claude/side-session-notes/bulletin.md` with the date, the commit or file, what changed, and who must act (user decision, 2026-11-13). Message directly only the sessions that asked for it, wait on it, or whose current work it changes, since each message wakes that session for a turn over its whole context.
- A session is the main session when the user designates it or, unless the user says otherwise (as a project's role list does with `(not main)`), once it has started another session for a task of the user's while no other session started it or after it was moved to the top level (user decisions, 2026-11-08 and 2026-11-13). Use the main session as the team lead, only for conversation and managing the sessions under it (user decisions, 2026-11-06 and 2026-11-13): answer there only from what you already know or what a handful of read-only calls shows in a session's result, such as its commit, report summary, or status, and when what you know describes a state that may have changed since (a screen, a file, a session), say where and as of when you learned it, or check it first (user decision, 2026-11-13), and start, check on, relay, and close sessions there. When it reports on several sessions or the user asks what is running, give one table of the open sessions with each one's topic, starter, state, and what waits on the user. Start everything else the user asks for in its own session right away without a separate proposal, even a single setting change: any change to files, settings, or apps, and any question that needs investigation such as reading files or transcripts, running commands, or searching. Send each task's follow-ups to its session and report each result in the main session in one or two lines. In a main session this replaces keeping just-decided work in the current session, even where the tool's own instructions would keep a continuation or a quick task there (user decision, 2026-11-13). Where the tool allows only a proposal, propose the session as above, and do the task in the main session only when it allows neither, saying so.
- When one request splits into parts that do not depend on each other, start each part in its own session at once without asking and run them in parallel (user decision, 2026-11-12).
- When parallel sessions share a lock or a numbered space, give each brief its identifiers in advance (section numbers, canvas areas, ports) and the session to hand the lock to next, so they neither collide nor wait for the main session to relay each handoff: numbers handed out on request collided three times (2026-11-10).
- A session under the main may start its own sessions for parts of its task that leave separate results, but those do not start more, so the tree stays two levels below the main (user decision, 2026-11-13): each session reports to the one that started it, which relays one line upward, and closes its own finished sessions before it reports its task done.
- Each time a session you started reports a finished turn, check right then whether its task is done: work committed and recorded, nothing waiting on the user (no open question or decision), and no session it started still working or waiting for the user. If so, close it in that same reply without asking, and say in one line which sessions you closed, that they can be reopened from the archive, and any proposals they left (user decision, 2026-11-09). Leave open a session that is still working or waiting for the user. Closing a session can also close the idle sessions it started, so list them right before closing; if one still waits for the user, leave both open and say why (user correction, 2026-11-09).
- Replace the main session itself once its measured context passes 80%, the same reading as the 80% line in `collaboration-core`, whose three choices it replaces for a main session (user decision, 2026-11-17), so the replacement finishes before automatic compaction near the window's end loses detail. Past the threshold, keep managing the sessions it started from the old main, starting new ones for new tasks as usual, until each has finished and been closed; then propose the replacement once, and on the user's yes save the open work (pending decisions, remaining tasks) to persistent memory, open the new main as a top-level session with an opening prompt that points to that memory (detach it right away if the tool starts it under the old main), and close the old main (user decision, 2026-11-09).
- Give a new session a short title of a few words naming its topic, and a project's role session its project and role (for example, “<project> design”), in the user's language (user decision, 2026-11-13 for role sessions). Leave scope or mode notes such as “(read-only)” out of the title and put them in the brief.
- Write a new session's brief and every later message to it in the user's language, as its title already is: a session started from a brief in another language drifts into that language in what it shows the user (user decision, 2026-11-09).
- Name in a new session's brief the skills its work will need under the skill triggers, such as `code-style` and `typescript` for app code or `ux-design` for design-tool work, and do the same in the prompt of a subagent that will write or review files (user decision, 2026-11-11).
- When a session you started needs the user's decision, ask the decision itself in its own terms with that session's recommendation and pass the answer on without a second question; never ask whether to relay an answer, and offer answering in that session as the other button (user decision, 2026-11-09).
- In a session another session started, ask the user's decision as the next-step box question, with the options in the closing message, and end the turn, never in a question dialog: an open dialog keeps the turn running, so an answer the starting session relays waits in the queue and stopping the session is refused; a hook sends such a dialog back (user decision, 2026-11-13).
- If closing a finished session is refused because a remote-control connection to it is on, turn the connection off and close it without asking, and say so in one line of the report (user decisions, 2026-11-06 and 2026-11-09). If it is refused because the session is still working, or because the app is keeping it for the user (open on screen or pinned), try once more when that session next reports or on your next turn, since both states usually pass within a turn; ask the user to close it from the session list, giving the reason, only when the session list shows it pinned or the second try is refused too (user decision, 2026-11-17).
- A scheduled run that edits a shared folder follows the one-writer rule in `collaboration-core` too: it takes the folder's edit lock and, when another editor holds it or uncommitted changes exist, skips the run and reports why.
- Check the shared to-do list for tasks other sessions handed to this session, finish those tasks, and then update the list.
- Shared notes folders, their index, and the shape of the reports in them follow the `report-writing` skill (user decision, 2026-11-16).
