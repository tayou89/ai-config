# Shared AI Configuration

This repository holds personal AI agent configuration for Claude Code and Codex: shared rules that apply to both tools, the Claude Code setup, and its Codex adaptation. It was renamed from `claude-config` on 2026-11-04; GitHub redirects the old URLs.

## Contents

- [Shared rules](shared-rules/) are the single tool-neutral source for project-independent principles: [skill triggers](shared-rules/skill-triggers.md), [working principles](shared-rules/work-principles.md), and [core collaboration](shared-rules/collaboration-core.md), which apply to every task, and [screen and UX design](shared-rules/design.md), [decisions and collaboration](shared-rules/decisions-and-collaboration.md), [running other sessions](shared-rules/sessions.md), [planning and research](shared-rules/planning.md), [writing, reports, and notes folders](shared-rules/reports.md), and [rule writing](shared-rules/rule-writing.md), which apply to their tasks.
- [Claude behavior rules](CLAUDE.md), `rules/`, `skills/`, `settings.json`, `scripts/`, and `mods/` (the usage panel shown beside the chat) are the Claude Code configuration, and [`scripts/install.py`](scripts/install.py) installs them. The repository root mirrors `~/.claude`, so a checkout there works directly. `rules/` and the `ux-design`, `decisions-and-collaboration`, `session-management`, `product-planning`, `report-writing`, and `rule-writing` skills are generated from `shared-rules/`; `emil-design-eng`, `review-animations`, and `apple-design` are unchanged MIT copies from `emilkowalski/skills` (commit `5206a95`), `grilling` is an unchanged MIT copy from `mattpocock/skills` (commit `4ae2317`), `humanizer-ko` is an MIT copy from `IsaacEryn/humanizer-ko` (commit `b1562c2`, version 1.5.0) with its Before/After examples moved into `references/pattern-examples.md` so the skill stays under the 20,000 characters restored after a compaction, `web-motion-techniques` and `web-interface-guidelines` wrap unchanged MIT references from `Motionsites-AI/claude-skill` (commit `faa30d5`) and `vercel-labs/web-interface-guidelines` (commit `434b7f9`); the other skills are written by hand, and `python` adapts a few tool lines from Astral's MIT `uv` and `ruff` skills (`astral-sh/claude-code-plugins` commit `f3ce88a`).
- [Project rules](AGENTS.md) hold the rules for work on this repository itself, such as its role sessions and where their areas meet; [`.claude/CLAUDE.md`](.claude/CLAUDE.md) imports them for Claude Code, while the root `CLAUDE.md` stays the global file installed for every project.
- [Codex global instructions](codex/AGENTS.md) contains the Codex-only engineering and workflow preferences and skill routing, followed by the always-relevant shared principles embedded from `shared-rules/`. - [Codex skills](codex/skills/) contains thirteen task-specific workflows adapted from the Claude skills (`knowledge-vault` among them, which only reads the vault), six skills generated from the shared rules, and unchanged copies of third-party design and planning skills, each with its license beside it: Anthropic's `frontend-design` (version 1.1.1 of the Claude plugin, Apache 2.0), since Codex cannot load Claude plugins, Emil Kowalski's `emil-design-eng`, `review-animations`, and `apple-design` (`emilkowalski/skills` commit `5206a95`, MIT), Matt Pocock's `grilling` (`mattpocock/skills` commit `4ae2317`, MIT), `humanizer-ko` (`IsaacEryn/humanizer-ko` commit `b1562c2`, MIT, the same as the Claude copy with its examples moved into `references/`), and `web-motion-techniques`, whose `references/` are the MIT technique, craft, spec, and review files of `Motionsites-AI/claude-skill` (commit `faa30d5`) under a skill file written here, without that skill's example prompts and media, and `web-interface-guidelines`, whose `guidelines.md` is the MIT `command.md` of `vercel-labs/web-interface-guidelines` (commit `434b7f9`) under a skill file written here. Refresh a copy when its source updates.

## How Each Tool Reads the Shared Rules

Claude Code loads every Markdown file in its user rules directory, including subdirectories, in every session. So only the always-relevant skill triggers, working, and core collaboration principles are generated into `rules/`, `CLAUDE.md` keeps only what is Claude's own (the hook list, the triggers of Claude-only skills, and settings sync), and the design, decision, and planning rules become Claude skills that load only for matching tasks.

Codex reads a single global `AGENTS.md` whole, without imports, and then the project instruction files from the project root down to its working folder, cutting the end of those project files once they reach `project_doc_max_bytes` (32 KiB by default); the limit covers project files only, not the global file (Codex source `codex-rs/core/src/agents_md.rs`, tested with codex-cli 0.163.0 on 2026-11-17). So the same three always-relevant files are embedded as the last sections of `codex/AGENTS.md`, after its Codex-only preferences, and the design, decision, planning, and rule-writing rules become Codex skills. [`scripts/sync-shared-rules.py`](scripts/sync-shared-rules.py) generates all of these copies from `shared-rules/`.

Every always-loaded line competes with the others for the model's attention, so the commit check runs [`scripts/check-rule-size.py`](scripts/check-rule-size.py) (user decision, 2026-11-12). It fails when `CLAUDE.md` and `rules/` together pass 32 KiB, when `codex/AGENTS.md` passes its own 32 KiB budget, and when the project instructions Codex loaded in any folder it worked in during the last 30 days (read from the Codex session logs) pass 85% of `project_doc_max_bytes`; project instructions above the 32 KiB default only warn, since a computer without the raised limit would cut their end. It also fails when the Claude or Codex global total differs from the size the user last approved, recorded in [`always-loaded-sizes.json`](always-loaded-sizes.json) (user decision, 2026-11-23), so growth needs the user's review and a trim keeps its freed room; `python3 scripts/check-rule-size.py --record` writes the measured totals there, and the approval stays the user's review of the rule text and the record change. Make room by removing or moving text, as the rule-writing rules describe.

## Apply on a Computer

Run [`scripts/install.py`](scripts/install.py) from a clone of this repository. It installs everything below into the Claude and Codex folders and refreshes them later; a second run changes nothing.

```bash
python3 scripts/install.py
```

```bash
python3 scripts/install.py --apply
```

The first command only shows what would change. The second writes it, after copying every file it replaces into `backups/ai-config-install-<time>/` inside the Claude or Codex folder. The script stops when the repository has uncommitted changes or is behind its upstream (`--allow-dirty` overrides this, and `--from-upstream` below avoids it), and when the `python3` (and on Windows `bash`) that the hooks call is missing, because a hook that cannot start lets every command through. Other flags:

- `--check` writes nothing and skips the plugin commands, so it takes under a second. It lists work in this checkout that is not committed, pushed, or pulled (fetching at most once an hour), repository changes not installed here, and what only this computer has: `settings.json` entries, Codex `config.toml` keys, lines in the merged instruction and rule files, and files in the configuration folders (`skills/`, `scripts/`, `agents/`, `commands/`, `output-styles/`, and the Codex `skills/`, `prompts/`, and `rules/`). It exits 7 when it finds any. Entries each computer decides for itself are listed in `PER_COMPUTER_SETTINGS` and keys the Codex app writes in `CODEX_APP_KEYS`; extend those lists rather than leave a difference unexplained.
- `--prune` moves installed files the repository no longer has (for example a retired file in `rules/`) to the backups folder; without it they are only listed.
- `--from-upstream` installs the commit that the default branch of `origin` points at, as last fetched, instead of the files in the checkout: it clones that commit into a temporary folder, runs that clone's own `install.py` with the same `--apply`, `--prune`, and `--first-merge` flags, and removes the clone. It asks `origin` for its default branch (falling back to `refs/remotes/origin/HEAD`) rather than reading the checkout's own upstream, so a run from a task branch or its worktree installs only merged work (user decision, 2026-11-13). Use it when the checkout holds work that is not merged and pushed, such as another session's unfinished edits; the record below stays on the checkout, so a second dry run shows nothing.
- `--checkout <path>` names the working checkout to record in `.ai-config-install/checkout` inside the Claude folder and to set `core.hooksPath` in. Without it, a run keeps a recorded checkout that still has `scripts/install.py`, so installing from another copy of the repository does not move the record; otherwise it records the checkout it runs from.
- `--first-merge keep-local` or `--first-merge use-repository` answers the one question the script cannot: when `CLAUDE.md` or the Codex `AGENTS.md` differs from the repository and no earlier install is recorded, are the differences this computer's own lines or stale lines to replace? Later runs merge three ways against the copy installed last time (kept in `.ai-config-install/base/`), so lines added on one computer survive and lines the repository removed disappear.

| Repository source | Destination in the Claude folder (`~/.claude`, or `CLAUDE_CONFIG_DIR`) | How |
| --- | --- | --- |
| `CLAUDE.md` | `CLAUDE.md` | Three-way merge |
| Each file in `rules/` | `rules/` | Copied |
| Each directory under `skills/` | `skills/<name>/` | Copied; skills not in the repository, such as a linked `ego-browser`, are left alone |
| `back-reference-hook.py`, `bulletin-hook.py`, `claude-commit.py`, `shell-guard-hook.py`, `shell_command.py`, `secret_files.py`, `commit_arguments.py`, `own_lines.py`, `session_writes.py`, `session_commits.py`, `session-writes-hook.py`, `reply-language-hook.py`, `plain-words-hook.py`, `config-sync-hook.py`, `main-session-hook.py`, `session_lineage.py`, `session_states.py`, `project_rules.py`, `sub-session-question-hook.py`, `pr-merge.py`, `local-integrate.py`, `worktree-cleanup.py`, `worktree-guard-hook.py`, `folder_owner.py`, `workflow_policy.py`, `integration_lock.py`, `integration_commands.py`, `report-check-hook.py`, `report_check.py`, `recommendation-change-hook.py` | `scripts/` | Copied (the maintenance scripts `check-codex-skills.py`, `check-commit.py`, `check-references.py`, `check-rule-size.py`, `install.py`, and `sync-shared-rules.py` stay in the repository) |

| --- | --- | --- |

The script then installs the Claude plugins that `settings.json` enables with `claude plugin marketplace add` and `claude plugin install`, and the Codex plugins in `codex/settings.json` with `codex plugin marketplace add` and `codex plugin add`. Claude Code would also fetch user-enabled plugins in the background after the first session starts, but installing them here makes the result immediate and checkable with `claude plugin list`. Plugins and connectors turned on for your claude.ai account (in the desktop app's Customize) arrive with the sign-in, not from this repository.

Conversation retention (user decision, 2026-11-13): `settings.json` sets `cleanupPeriodDays` and `desktopSessionCleanupPeriodDays` to 90, so Claude Code deletes transcripts under `~/.claude/projects/` once they are older than 90 days (Claude Desktop and Cowork transcripts must pass both limits, and the second key needs Claude Code 2.1.248 or later and is read only from user or managed settings). Both keys are replaced from the repository on install, and scripts that read transcripts see only the last 90 days; decisions and lessons kept in the knowledge vault remain.

Keep the Codex skills beside AGENTS.md as installed so its relative references resolve. Check `AGENTS.override.md`, which takes precedence over the global AGENTS.md. Do not place these Markdown rules in `~/.codex/rules/`, which Codex uses for command execution policies. After an install, confirm with `codex debug prompt-input` that the end of a long project AGENTS.md is included (non-Latin text takes several bytes per character, which is why `project_doc_max_bytes` is raised). Start a new conversation to load the complete instruction set.

### A new computer

The script does not install apps or sign in. On a new computer, in this order:

1. Install the apps and command-line tools.
   - macOS: Command Line Tools (`xcode-select --install`, which brings `git` and `python3`), the Claude app, the ChatGPT app, Node.js, the GitHub CLI (`gh`), Claude Code (official installer), and the Codex CLI; also Figma, Chrome, and ego lite if you use them.
   - Windows: Git for Windows (it provides Git Bash, which Claude Code uses to run the hooks), Python 3 with `python3` available in Git Bash, the Claude app, the ChatGPT app, Node.js, the GitHub CLI, Claude Code, and the Codex CLI. This setup has not been run on Windows yet, so run the dry run first and read its notes.
   - Linux: `git`, `python3`, Node.js, and the GitHub CLI from the distribution's packages, Claude Code (official installer), and the Codex CLI; the Claude desktop app has a Linux beta installed with apt. This setup has not been run on Linux yet either, so run the dry run first and read its notes.
2. Sign in yourself: the Claude app and `claude`, the ChatGPT app and `codex login`, and `gh auth login` (HTTPS, credential in the system keychain). Set `git config --global user.name` and `user.email`.
3. Clone this repository and run the dry run, then `--apply` (with `--first-merge` if it asks).
4. In a Claude session, run `/mcp` and authorize the plugin servers you use. Plugins a project enables only for itself (`--scope local` or `project`) are not installed by this script; install them again in that project.
5. Set what each computer keeps for itself: the Claude app's own settings (Settings → Claude Code: notifications, keep awake, browser, the Remote Control default; the branch prefix and auto-archive on pull request close follow the account), the Codex app's display settings, and, on a computer that holds the knowledge vault, `KNOWLEDGE_VAULT_DIR`, the folder the `knowledge-vault` skill reads, in two places: the `env` of the installed `settings.json` for Claude, and `[shell_environment_policy.set]` of the installed Codex `config.toml` for Codex, which passes it to the commands Codex runs (the repository leaves both out so each computer keeps its own path; the install script treats that Codex table as the app's and leaves it alone). The `code-plan` skill adds `claude-plans/` to the global gitignore the first time it runs.

Project data outside git (Claude's auto memory and transcripts under `~/.claude/projects/`, the desktop app's scheduled tasks under `~/.claude/scheduled-tasks/`, the desktop app's session notes under `~/Library/Application Support/Claude/side-session-notes/`, the project notes and their copies under `~/Documents/session-notes/` and `~/Documents/session-notes-backup/`, review material) is not part of this repository. Auto memory is kept per computer, in a folder named after the project's path, so keep the same user name and project path when copying it.

## Maintenance

Whether each app session works, waits for the person (a finished turn that asks, an open question, or a permission prompt), or finished unread is decided in one place, [`scripts/session_states.py`](scripts/session_states.py), for the usage panel and for the AI work dashboard (a separate repository): every 5 seconds one session's panel reads the app's session list and writes the result to `~/Library/Caches/usage-panel/session-states.json`, which the other panels read and the dashboard is to read. After changing it, run `python3 -m unittest tests.test_session_states`.

Every install that changes a file under `mods/` reloads that mod in every open session, and each shows a reload line, so mod changes are merged in batches (user decision, 2026-11-18): a finished mod change waits until the other mod changes already under way (open pull requests or task worktrees touching `mods/`) are ready and merges with them, at most twice a day, except a fix for a broken mod or a change other work is waiting on, which merges at once.

Edit shared principles only in `shared-rules/`, in English and without tool- or project-specific details. Then run `python3 scripts/sync-shared-rules.py` to regenerate the Claude and Codex copies, and `python3 scripts/sync-shared-rules.py --check` to confirm they match before committing. When adding a rule file, register it in the script as always-loaded or task-scoped (the check fails on unregistered files in `shared-rules/` or `rules/`) and update the contents above. Edit the Codex-only part at the top of `codex/AGENTS.md` by hand, but not its generated sections, which the script replaces.

The commit check also runs [`scripts/check-references.py`](scripts/check-references.py) (user decision, 2026-11-16), since a rename or a move breaks the pointers between rule files without any error. It reads every Markdown file the repository holds, so a rule file in a new place, such as this repository's own [AGENTS.md](AGENTS.md), is checked without being listed (user decision, 2026-11-24); in a Git work tree these are the files Git would commit, which leaves out other worktrees and ignored files. It fails when a relative link, a quoted section of a skill, a rule, or an instruction file (hook messages included), a skill a document says to load, a `scripts/`, `tests/`, `rules/`, or `shared-rules/` path in code, or an `@path` import in a file Claude loads as instructions (a `CLAUDE.md`, a file in `rules/` or a `.claude/rules/` folder, and what they import, to the four hops Claude follows) points at nothing for the tool that reads the document, and when the notice tags `CLAUDE.md` lists differ from those the hooks emit. What counts as an import follows Claude Code 2.1.319 and its [import documentation](https://code.claude.com/docs/en/memory#import-additional-files), and the script's own description lists where it differs; imports of this computer's paths or of files outside the repository are not checked. It skips fenced code, the `shared-rules/` sources, whose generated copies it checks, and third-party skill copies (a skill folder with its own license file). After changing it, run `python3 -m unittest tests.test_check_references`.

Install `scripts/` as a whole: the shell guard hook (`shell-guard-hook.py`) and the commit wrapper (`claude-commit.py`) import `shell_command.py`, `secret_files.py`, `commit_arguments.py`, and `session_writes.py` (which imports `own_lines.py` and `shell_command.py`) from beside them, the wrapper also imports `session_commits.py`, the write-record hook (`session-writes-hook.py`) imports `session_writes.py`, and a hook that cannot start lets every command through. The write-record hook keeps each session's record in `session-writes/` inside the Claude folder and deletes records older than 14 days, the age after which Git may prune the file contents they name. A call whose snapshot cannot be taken, such as one that moves a repository away, is recorded as an unknown write over what that snapshot covered while the call ran, so the wrapper refuses another session's lines only when they were written while that call ran. A command that cannot change working trees takes no snapshot: reading programs and git index work, such as a commit through the wrapper, a `git push` to network remotes in a repository without `pre-push` or `reference-transaction` hooks and without settings that make a push run a program here, `gh auth`, and gh commands that only show pull requests and runs (user decision, 2026-11-16). A call a hook or the user stopped before it ran stops covering at its result in the transcript. The shell guard keeps the contents its `--include-unrecorded` dialog lists lines from, in `offered-includes.jsonl` beside the record, and the wrapper commits exactly those contents, refusing a file that changed after the dialog; it keeps each such call it runs as approved, since the shell guard asks before such a call and a declined call never runs, so a retry whose files still hold the approved contents is not asked again, whatever else runs meanwhile. `worktree-cleanup.py` checks for other processes working in a worktree (`integration_commands.py`). The wrapper, the worktree guard, and the start-session hook read a linked worktree's owner through `folder_owner.py`, which keeps it in `claude-owner.json` in that worktree's own Git folder and imports `session_lineage.py`, `workflow_policy.py`, and `integration_lock.py`; the shell guard and `session_writes.py` also import it, to tell a task worktree apart and to take one over; after changing it, run `python3 -m unittest discover -s tests -p 'test_*owner*.py'` as well. The wrapper lists each commit it makes beside the session's record, so `--amend` rewrites only that session's commits. After changing any of these nine scripts, run `python3 tests/test_shell_guard.py`; add `--table` to print every case with its decision. The skill gate (`skill-gate-hook.py`) also imports `shell_command.py`, `motion_values.py`, and `skill_gate_records.py`, which holds its record folder layout and the choice record it shares with `choice-shown.py`, so after changing any of them, run `python3 -m unittest tests.test_skill_gate_hook tests.test_choice_shown` as well. After changing which files `shell_command.py` counts as written (redirections, `tee`, and in-place `sed` and `perl`, read under both the macOS and GNU sed conventions), run `python3 tests/test_shell_command.py` too.

The reply-language hook (`reply-language-hook.py`) imports nothing from beside it. It reads the language the user reads in from `REPLY_LANGUAGE` in the `settings.json` `env` and does nothing when that is unset; before a tool draws a task list, next-step box, question dialog, file caption, or session title, it denies text in another language, and after each tool call it reminds the model when the transcript shows a progress line in another language. When a turn ends, the Stop hook reads `last_assistant_message` and continues the turn once (`[REPLY LANGUAGE]`) when that closing message is in another language, skipping when `stop_hook_active` is set, and moves the transcript check position past it so the next reminder does not repeat it; right after a compaction (`SessionStart`, matcher `compact`) it adds a one-line language note. Half the sessions, those whose session id has an even first byte of its SHA-256, get the reminder and that note written in the user's language and the rest get them in English, a measurement to read around 2026-11-21 before the losing variant is removed (user decision, 2026-11-18). Replayed over the 97 transcripts active from 2026-11-16 to 2026-11-18, the closing check would have continued 18 of their 967 closing messages, all of them in English. After changing it, run `python3 -m unittest discover -s tests -p test_reply_language.py`.

The plain-words hook (`plain-words-hook.py`) imports nothing from beside it and reads only the tool input. Before a next-step box (`wrap_up` recap, ask, and reply buttons) or a question dialog is drawn, it denies one that holds a commit number, a command option, an exit code, a file name or path, or code, leaving links, web addresses, and session ids alone. A next-step box that asks a decision and passes gets a `[PLAIN WORDS]` notice before the closing message is written: describe each choice by what it does, without developer words, labels from a brief or another session, or names coined earlier. It does not check the closing message or list borrowed labels, since a replay showed that quoted labels in briefs were mostly the user's own answers, screen copy, and session names. Replayed over transcripts from 2026-11-06 to 2026-11-17, it would have denied 922 of 2,341 boxes before the plain-replies rule went in and 5 of 83 after it, all of them real commit numbers, and noticed 52 of those 83. After changing it, run `python3 -m unittest tests.test_plain_words_hook`.

The back-reference hook (`back-reference-hook.py`) imports nothing from beside it. It looks for Korean and English words that point back to earlier chat text ("앞서 보여 드린", "앞 답변", "shown earlier") and leaves quoted text alone. A next-step box (`wrap_up` ask and reply buttons) that has such a word, or one pointing elsewhere such as "아래 내용", "이 메시지", or "7절", gets a `[BACK-REFERENCE]` notice before the closing message is written. A question dialog with such a word and no link, path, or preview is denied. A closing message with a sentence that asks something and has such a word is continued once, unless that paragraph or the one before or after it has a file link, path, quote, or code block, or the sentence introduces the text ("아래와 같습니다"); a list alone does not count as showing it. The Stop hook reads `last_assistant_message` and skips when `stop_hook_active` is set. Replayed over all transcripts from 2026-11-06 to 2026-11-13, it flagged 31 of 1,699 next-step boxes, 0 of 71 question dialogs, and 6 of 2,572 closing messages, 2 of those 6 wrongly. After changing it, run `python3 -m unittest tests.test_back_reference_hook`.

The recommendation-change hook (`recommendation-change-hook.py`) imports nothing from beside it. It looks for Korean and English words that say a recommendation changed ("추천을 E로 바꿨습니다", "추천이 …로 바뀌었습니다", "changed my recommendation") and leaves quoted text, code, a sentence that relays another session's or a reviewer's change, and option labels such as "(추천)" or "추천대로" alone. A next-step box (`wrap_up` recap, ask, and reply buttons) that says so gets a `[RECOMMENDATION CHANGE]` notice of what evidence allows a change before the closing message is written. A closing message that says so is continued once, unless that paragraph or the one before or after it says when the evidence appeared ("처음 얻은", "만든 뒤에 나온", a date, "first appeared"); the hook cannot judge whether the evidence is real, and any such word or a date in those three paragraphs counts. Both notices end by saying that when the evidence appeared is its order against the earlier recommendation or a time read from a clock or a record, since a session once wrote times it had not read (2026-11-18). Only a sentence where "추천" takes a particle (을, 은, 이, 도, 으로) counts, a question does not, and English matching is best effort. The Stop hook reads `last_assistant_message` and skips when `stop_hook_active` is set. Replayed over all transcripts from 2026-11-06 to 2026-11-17, it noticed 18 of 1,921 next-step boxes and continued 32 of 3,234 closing messages, about 5 of those 32 recounting past changes or describing a rule rather than making a change. After changing it, run `python3 -m unittest tests.test_recommendation_change_hook`.

Every commit in this checkout runs `.githooks/pre-commit` (`install.py` sets `core.hooksPath`), which copies out the index being committed and runs the sync check, the reference check, the rule size check, the Codex skill check, every test, and the token scan in that copy. Commits need no approval (user decision, 2026-11-09), so this check is where a broken rule copy or script is stopped; do not bypass it with `--no-verify`. The hook runs the committed copy of `check-commit.py` from the copied index, so the list of checks comes from the commit too and another session's half-finished edit to that script or its checks does not decide other commits; only the hook's few lines run from the working tree. The commit wrapper holds the checkout's lock (`integration_lock.py`) while this check runs, so a second commit through the wrapper waits instead of checking a base about to be replaced (a plain `git commit` takes no lock), and a private-index commit lands on the newer HEAD when that HEAD, on the same branch, holds its files as they were; the `git-commit` skill lists the conditions. After changing `scripts/check-commit.py` or the hook, run `python3 -m unittest tests.test_check_commit`.

The pull-request check (`.github/workflows/checks.yml`) runs one job, `checks`, on every pull request and every push to `main`, whatever paths change: `check-commit.py --against <base>` runs the same checks on the checked-out tree with the macOS system Python 3.9 and scans the lines added since the base for tokens, because a merge made on GitHub skips the local hook. It is the required check a repository names when it adopts the pull-request workflow below.

The worktree workflow tools (user decision, 2026-11-13) serve repositories whose committed `.agent-workflow.json` names a mode, its base branch, and its required checks (`pull-request`) or check commands (`local-integration`); `workflow_policy.py` reads and checks that file, `integration_lock.py` holds one integration at a time per repository in the shared Git folder (the commit wrapper takes the same lock in the Git folder of the checkout it commits in, so commits in the original checkout queue with integrations), and `integration_commands.py` holds their command helpers and exit codes. `pr-merge.py` merges a task's pull request only when its head contains the current base and every required check passed on that head, with `--match-head-commit`, reading the policy from the fetched base branch, then fast-forwards the task branch to the merged head; with `--wait` (user decision, 2026-11-17) it first waits for the required checks, and when the base moved, the merge is clean, and the checks passed, it brings the base into the head through GitHub's update-branch and waits again while holding the lock; `local-integrate.py` merges a task branch onto the base in a temporary worktree, runs the check commands there, and fast-forwards the original checkout only when they pass; `worktree-cleanup.py` removes a task's worktree and branch only after its work is committed, integrated (by the merged pull request's head, since a squash merge leaves no ancestry, or by ancestry after a local integration), and no other session's process has its working folder there. The lock covers the sessions that share one clone: a merge on GitHub's website or from another computer between the check and the merge is not stopped, and `pr-merge.py` then warns that the merge landed on a base it did not check. The required check runs the pull request's own workflow and scripts, so `pr-merge.py` warns when a pull request changes `.agent-workflow.json`, `.github/workflows/`, `.githooks/`, or `scripts/check-commit.py`. Their tests run against disposable repositories, with `tests/github_double.py` standing in for `gh` over a local bare repository: `python3 -m unittest discover -s tests -p 'test_pr_merge.py'`, and likewise `test_local_integrate.py`, `test_worktree_cleanup.py`, and `test_worktree_guard_hook.py`. Every repository records its workflow there (user decision, 2026-11-17): `direct` commits straight to the base branch and `team` follows a team's rules from a copy listed in `.git/info/exclude`; neither uses worktrees, so the worktree guard leaves their original checkout writable and `worktree-cleanup.py` refuses them. The commit wrapper commits nothing (exit 11) in a checkout whose `.agent-workflow.json` is missing or unreadable, and says to ask the user which mode the repository uses; `test_workflow_required.py` covers this. For its large-change review, the wrapper counts a merge of one branch only by what differs from Git's automatic merge of the two sides (conflict resolutions and hand edits); `test_merge_commit_count.py` covers this.

## Hooks

`CLAUDE.md` lists in a few lines what the hooks enforce; this is how each works.

- **git-commit**: a hook denies direct `git commit`; the skill commits through `scripts/claude-commit.py`, whose `git commit` subprocess the hook does not see. In a session started after the write-record hook (`scripts/session-writes-hook.py`) was installed, the wrapper also refuses staged lines that the session's record does not show as its own, and `--own-lines` stages only the session's lines (user decision, 2026-11-09), leaving out silently only changes that other sessions' records lead to: a change after the session's write that no record explains, such as a project hook rewriting its line, is asked about instead (user decision, 2026-11-16). After the session commits its lines while another session's stay uncommitted, the next commit reads that commit from Git history and the file as the records show it then, so it knows which lines went in instead of matching blank lines and common headings by text; a commit the records cannot trace changes nothing (user decision, 2026-11-18). It names every such file in one refusal, and says whether another session's edit, only another session's command, or neither overlapped the lines it cannot prove. A project hook whose command runs through `session-writes-hook.py --around` (a formatter, say) has its rewrite recorded as the session's write: the wrapper waits for the call's own record, since Claude Code runs matching hooks in parallel, and the rewrite counts as contested when another session's call overlapped it (user decision, 2026-11-16). In a linked worktree a Claude session's commit reads the folder's owner instead: the owner session commits whole files whoever wrote them (Codex, a formatter, a person at a terminal there), any other session is refused (exit 12), and while the worktree guard has recorded calls it let through there unjudged it commits only with `--accept-gaps`, which the guard asks the user about once (exit 13); `--own-lines` and `--include-unrecorded` only print a note there (user decision, 2026-11-18). A session that takes over another session's uncommitted files runs `session_writes.py adopt --from <session> <file> ...` first: that session's recorded writes to them up to then count as its own, while other sessions' lines and that session's later writes stay theirs (user decision, 2026-11-17). With `--no-stage`, the shell guard's dialog shows, and the wrapper commits, the prepared index's content, so a retry with the same content is not asked again. The record hook takes no snapshot for a wrapper call; where commit hooks may change files, the wrapper records only their run, so a commit waiting for the dialog holds up no other session (user decision, 2026-11-17). It refuses `--amend` unless HEAD is a commit the session made through it and has not pushed (user decision, 2026-11-11).
- **shell guard** (`scripts/shell-guard-hook.py`, user decisions 2026-11-08 and 2026-11-09): for Bash, Monitor, and terminal-tab commands, after expanding shell aliases and functions, wrappers, `sh -c`, `eval`, scripts, `cd`, and `git -C`, it denies direct `git commit`, a commit-wrapper call whose file list is known only at run time, and staging `.env` or credential files (the commit wrapper also refuses them, live-looking tokens on added lines, and a large code change without `--reviewed`). It asks the user before a push that is not routine (force, deletion, mirror, tags, all branches, another remote or ref, unknown options, or a repository with `shellGuard.askBeforePush` set), before production, staging, or live-mode runs (environment variables such as `NODE_ENV=production`, options such as `--env production` or `--mode live`), and before a commit-wrapper call with `--include-unrecorded`, which commits lines the session's write record does not show as its own, listing those lines as the one question about them, except for a retry whose files still hold the approved contents (user decisions, 2026-11-11 and 2026-11-16), and before `session_writes.py adopt` takes over files from a session the app has not archived (user decision, 2026-11-17), neither in a task worktree, where the worktree guard asks before a takeover instead (user decision, 2026-11-18); a routine push of the current branch to its own remote passes without a prompt. It denies `gh pr merge`, and `gh api` sending PUT to a pull request's merge endpoint, in a repository whose `.agent-workflow.json` names the pull-request mode, pointing to `pr-merge.py`, asks before such a merge anywhere else (a team's repository, one without the file, or one named with `--repo`), and asks before a push of the base branch of a pull-request repository (user decision, 2026-11-13).
- **worktree guard** (user decision, 2026-11-13): `scripts/worktree-guard-hook.py` keeps the original checkout of a repository whose `.agent-workflow.json` names a worktree mode read-only: it denies Edit, Write, and NotebookEdit of a file Git does not ignore there, shell writes onto such a file (a redirection, `tee`, `sed -i`, `perl -i`, `rm`, `mv`, `touch`, `mkdir`, the destination of `cp` or `ln`), Git commands that change the working tree, the index, or HEAD there, and the commit wrapper run there. Reads, `git fetch`, `git worktree add`, and files Git ignores such as `claude-plans/` pass. In any folder of such a repository it denies `git worktree remove` and `move`, which skip `worktree-cleanup.py`'s checks. Each linked worktree, in any repository, has one owner session (`scripts/folder_owner.py`, user decision, 2026-11-18), recorded after `git worktree add` or `EnterWorktree` and when a session starts in a worktree the app made for it; a worktree made before owners were recorded, or whose owner the app archived, goes to the next session that writes there, which the guard asks the user about first when the worktree holds uncommitted changes. Another session may only read in an owner's worktree while the owner is open or its state is unknown: the guard denies its file tools there, shell writes there, and any call whose program is not a known reader (reading programs, read-only Git and `gh` commands, `sed -n` printing, and `codex exec` with a read-only sandbox) that runs there or names a path there, and a command it cannot follow that names such a folder. In a shell command, the text `echo`, `printf`, `cat`, or `tee` writes to a file counts, joined as given rather than formatted; so does a `sed -i` or `perl -i` expression with a time or easing function on a style sheet or on a file that holds motion, and a `codex` prompt with the input codex appends to it; a prompt read from a file (`"$(cat brief.md)"`, `< brief.md`) is checked when that file is written, and text that passes through other programs in a pipeline is judged as the parser hands it on. It is a text heuristic: a sentence about switching or timing that is not visual motion ("서버 전환 후 5초") counts too, and so does a formatting change inside a piece of motion; it checks the caller and not the session or agent that receives a brief, and motion proposed only in a reply is out of its reach. In a session that has loaded `ux-design` at any point, compactions included, each choice question (a dialog question with two or more options, or a next-step box with two or more buttons and no app action, since such a box asks to go ahead with a step) also needs a record made beforehand with `python3 ~/.claude/scripts/choice-shown.py --question "<question>" --option "<label>" "<file or link>"`, one `--option` per option, or `--not-visual "<why>"` in place of the options (user correction, 2026-11-18). The hook compares the question with its spacing normalized and refuses until every option label is in a record of that question, so asking again unchanged is refused again, a renamed option needs its own record, and a record keeps serving the same question and labels for the rest of the session; a box with buttons but no question is refused until it has one, and no word list exempts a question, so a screen decision worded like a merge is checked too. The command records only a file on this computer (a path or a local `file://` address) or an http(s) link with a host, under the session in `CLAUDE_CODE_SESSION_ID`, in `choices.jsonl` beside that session's skill records, which the 14-day cleanup removes once no event has touched the file for that long. A record is the session's own declaration: the hook cannot tell whether the user saw the file, whether the options were drawn at the same fidelity, or whether moving options play at their intended speed, and a subagent shares its session's record. A choice record that cannot be read lets the question through with a note on stderr. It records each Skill call and each slash command the user types in `skill-gate/` inside the Claude folder, one file per session and subagent, and deletes record files no event has touched for 14 days. A subagent counts only its own loads, a fork also counts its parent's, and an agent type without the Skill tool is not checked. After a compaction only the skills the compaction restored count, read once from the `invoked_skills` attachment that follows its boundary in the transcript. For every agent, gated or not, a write that would create a new file in a session folder (`local_…`) of `side-session-notes/` (Write, Edit, NotebookEdit, or a shell command's redirection, `tee`, `sed -i`, or `perl -i`) is refused with the project notes folder to use instead, since the app deletes those folders without the Trash; edits to files already there pass, and `SKILL_GATE` off turns this refusal off too (user decision, 2026-11-23). A hook failure lets the call through. `"SKILL_GATE": "off"` in the `settings.json` `env` stops the refusals while loads are still recorded; running sessions pick up the change at their next tool call (tested 2026-11-12 with a project settings file).
- **plan reminder**: before Edit or Write of `claude-plans/plan-*.md`, a hook adds `[PLAN CODE REMINDER]` (plan sample code follows the same rules). Non-blocking.
