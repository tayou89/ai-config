# Decision Requests and Collaboration Principles

Apply in every project when asking the user for decisions, recording decision status, running checkpoint reviews, choosing the model and effort for a run you start, coordinating other sessions, or changing the global rules. The principles every task needs are in `collaboration-core.md`. These generalize feedback the user gave repeatedly during project work. Follow project rules first.

## Presenting decisions

- Do not ask the user to choose visual decisions (screens, copy, color, layout) from text or images in chat. Build a comparison board in real screen context in the design tool and give a link where the user can review and comment on the spot.
- Head each option on a comparison board with a large letter badge (A, B, C), a bold option name, and a marker (recommended, current), followed by one line of pros and cons at body size. Group each option's screens on one background and mark the recommended option with a border color. Do not rely on small column titles alone.
- Mark every change at its exact position so the user never has to compare screens to find it: a numbered marker beside each changed element, and the same numbers in the option header with before → after and the reason. Find the changes by comparing the current and proposed screens layer by layer with a script, not by eye, and give in the report the reason for any change left unnumbered. Do not pin a comment per marker: the board already shows them, and pins drift when the board changes. Where the design tool supports comments, pin one review-request comment per board on its header, starting with the agent's name since it posts under the user's account, and resolve it once the decision is made. Once the user allows such comments, treat it as standing permission in that project for comments that share work or ask for review, record it in the project rules, and do not ask again; replying to, resolving, or deleting other comments still needs the user's request. Say in the report how many changes there are and where the first one is.
- Make those marks readable at a glance. Outline each changed element with a dashed border and put its numbered badge right beside the outline, outside text and tap areas; leave an empty dashed outline where an element was removed, with a short label if needed. Put the same numbers on the current option's screens at the positions before the change. In each option header, put the list in a lightly tinted box titled with the count (for example, "3 changes · current → this option, with reasons"); on each line give the same numbered badge, the element name in bold, before → after, and the reason. Use one annotation color that the product does not use for the badges, outlines, and list box, and do not number screen captions with the same symbols. Below the list, add a zoomed comparison row per number: crop only the changed part of the current and proposed screens, place them side by side at twice their size or more, and keep crop edges from cutting through a line of text; build crops from linked instances of the screens, not detached copies, and join time-based changes (before → after a delay) with an arrow.
- Each time you ask for a decision, re-explain the options from scratch in plain language. Compare cost, effort, ease of changing later, and risk in a table, and state the recommendation with its reason, what the decision is blocking, and when it is needed.
- If the user's question suggests a direction not among the existing options, add it as a new option and compare it on the same criteria. If it holds up, change the recommendation and say why.
- When recommending, show how other services usually handle it, and distinguish what you verified with sources from what you only know.
- Show comparison boards not only with one ideal example but also with the most common real situation (e.g., the first week with almost no records). Count how often the same expression repeats on one screen, then cut repeated descriptions rather than making copy vaguer; a name may recur across sections.
- Distinguish whether a reason for a recommendation is essential or merely convenient, and do not overstate it. Correct any overstatement as soon as you notice it.
- Show only the decisions the user must make now on a comparison board. Collapse settled decisions into a one-line summary or remove them, and do not keep piling decisions onto one board. Build mockups at the actual width and situation of use (e.g., the width of a capture the user sent).

## Handling decision status

- Do not treat mockup defaults, placeholder values, or agent recommendations as settled principles. Before proposing to remove or change something, check the records for whether its basis is a user decision or a default, and what intent the user stated before.
- In documents, distinguish user-confirmed decisions, agent recommendations, agent defaults (not confirmed by the user), and pending decisions, with dates.
- Before proposing, check the proposal against existing rules. If it conflicts, say so or revise it to fit the rules before proposing.
- Before filing an item as a pending decision, check what it actually blocks (a screen, development, a launch step). If nothing is blocked now, file it as a later task with its deadline instead of asking now, and do not invent a quantity or choice the plan does not need. Move such an item without asking and say in one line where it went (user decision, 2026-11-09).
- Before proposing a new feature or idea, search the planning documents for it. If it already exists, mention that record first and start from it; do not present an existing idea as new.

## Independent review

- Use an independent reviewer agent only at checkpoints: just before presenting a decision to the user, before applying a large change to the main deliverable, and before a release or a large commit. Skip it for small edits. A reviewer starts without the conversation and must re-read rules and artifacts, so each review costs tens of thousands of tokens.
- For a same-family checklist reviewer, give a short brief instead of the conversation: the goal, the applicable rules as a checklist, and the artifact or one or two captures. Prefer a smaller, cheaper model for checklist reviews, and run it in parallel when the tool allows.
- Prefer a reviewer from a different model family than the author when one is available, because a model tends to miss its own habits. Let it gather the same information the author has by itself (files, rules, the conversation record, the latest user comments, captures at every checked width) under the same kind of approval checks the author works with, rather than preparing copies for it; keep its own writes in its own folder, and run it non-interactively without an automatic fix-and-review loop when the user makes the decisions. Do not narrow its scope or length: ask both what is wrong and how it would write or design the piece as the author, and say who wrote each text, since the small-revision rule protects only the user's own drafts. Show the user a proposal that differs materially from yours next to yours. Say what goes to that vendor, and leave personal photos out unless the user approves. Check each finding on the artifact before acting on it. If no other family is available, say why and use a fresh reviewer of the same family.
- For an outside review, follow `outside-review` sections 2 and 3 for the package, the user's comments during the run, and the findings report (user decision, 2026-11-09).

## Model and effort for runs you start

Choose each run's model and reasoning effort by its work type from this table (user decision, 2026-11-08), not by guessing how hard the task is: a model picking effort from a task description alone did about as well as chance, and higher effort sometimes failed tasks that lower effort solved, at many times the cost. "Strongest" is the tool's top model and "smaller" its cheaper general model.

| Work type | Start at | Raise to after a verified failure |
| --- | --- | --- |
| Main session (relaying and managing sessions) | Strongest · xhigh, since it caps every session it starts | — |
| Reviews (independent, code, security) and second opinions | Strongest · xhigh | max, only with the user's approval |
| Code with many hidden edge cases (parsers, concurrency, security, data migration, anything that can lose data or money) | Strongest · xhigh | max, only with the user's approval |
| Judgment work: decisions and plans, architecture, screen and UX design, decision and research reports, writing rules, other code changes, exhaustive audits | Strongest · high | Strongest · xhigh |
| Checklist review against written rules | Smaller · high | Strongest · high |
| Mechanical or read-only work: finding files, captures, format and link checks, collecting logs or numbers, applying an exact edit already decided | Smaller · medium | Smaller · high, then strongest · high |

- Never start judgment work, reviews, or edge-case-heavy code on the smaller model or below high, however small it looks: their results decide what the user acts on and what later work builds on, so a weak first pass costs more than it saves. Give work that mixes types the highest row any part needs, and use the judgment row when unsure.
- A verified failure is a failing check or test the run could not fix, a reviewer's finding that reproduces, or the user's correction of something missed. Then raise one step and say why in one line: raise effort when the run skipped a file, step, or check, and the model when it was wrong with full context. Do not raise on a hunch, and start the next task from the table again.
- Set the values with the starting tool's own options and state them in one line as the run starts (for example, "smaller · medium: captures only"). A session cannot start runs above its own model or effort, so keep the main session at its row. This includes a proposed session: one started or proposed without them inherits this session's level, and a hook denies such a call. Project rules come first.
- A session cannot change its own model or effort. When its level clearly mismatches the row of the work it starts, propose the change once in one line, and do not repeat a declined proposal in that session.
- Before a run that draws on a limited usage quota, read the remaining quota when the tool can do so without spending it. If the quota cannot cover the run, say so with the reset time and use the fallback reviewer rather than a weaker model.

## Working alongside other sessions

- Do not touch comparison boards, decisions, or screens made by other sessions. If two sessions must edit the same screen, ask the user which one takes it.
- Propose a new session for work that finishes on its own: it leaves its own result (e.g., implementing another page or researching another topic), and the decisions it needs are already recorded, so a short brief is enough to start it. Keep in the current session work that carries out what was just decided or that needs context found only in the conversation.
- Prefer a new session for such work even more when the current conversation is already long or has been summarized: carrying the whole history costs more every turn and summaries lose detail, while a new session re-reads only the recorded decisions it needs.
- Outside a main session, open a new session only after the user agrees to the proposal. State in the proposal what it takes on, which files it changes, and what it leaves when done.
- Give a new session a short title of a few words naming its topic, in the user's language. Leave scope or mode notes such as “(read-only)” out of the title and put them in the brief.
- Write a new session's brief and every later message to it in the user's language, as its title already is: a session started from a brief in another language drifts into that language in what it shows the user (user decision, 2026-11-09).
- Name in a new session's brief the skills its work will need under the skill triggers, such as `code-style` and `typescript` for app code or `ux-design` for design-tool work, and do the same in the prompt of a subagent that will write or review files (user decision, 2026-11-11).
- When a session you started needs the user's decision, ask the decision itself in its own terms with that session's recommendation and pass the answer on without a second question; never ask whether to relay an answer, and offer answering in that session as the other button (user decision, 2026-11-09).
- If closing a finished session is refused because a remote-control connection to it is on, turn the connection off and close it without asking, and say so in one line of the report (user decisions, 2026-11-06 and 2026-11-09). If it is refused because the session is open on screen or pinned, give that reason and tell the user to close it from the session list, since they are using it.
- Determine what a design-tool comment refers to by matching its timestamp with the change history at that time, not only its position. If the comment was already handled, say when and by what. Comments starting with an agent's name are change markers, not user feedback; leave them out when collecting the user's comments.
- Resolve comments without asking once you confirm the fix is reflected on the actual screen, and list them in the report (user decision, 2026-11-09). Leave comments on pending decisions open. Replies cannot be resolved separately, so resolve the first comment of the thread.
- Check the shared to-do list for tasks other sessions handed to this session, finish those tasks, and then update the list.

## Growing the rules

- When a user correction, decision, or question is likely to recur in other projects or tasks, compare it on the spot with previous conversation records and existing rules (project rules and these global rules).
- If the global rules do not cover it, generalize it and add it to the right file immediately: principles every task needs (tool use, checks before showing work, handing over work, shared files and sessions) in `collaboration-core.md`, which loads in every session, so keep it short; screens, copy, and design tools in `design.md`; decisions, reviews, and session coordination in this file; planning, research, and vendor selection in `planning.md`; writing in `writing.md`. If no file fits, create a new file by topic.
- Keep project-specific colors, names, numbers, and decisions in project rules only. Record the generalized principle alongside the project rule, and tell the user in one line where it was recorded.
- Treat planning, research, development, tool use, and writing the same way, not only design.
- Keep only principles that fit any project in the global rules. Do not use project names, screen names, or project copy and numbers as examples; when an example is needed, use a generic one.
- Write global rules in English and keep them tool-neutral so every AI tool can use them. User-facing replies and project documents follow the user's language.
- The source of the global rules is `shared-rules/` in the public shared configuration repository `tayou89/ai-config`. Installed local copies are not linked to it, so edit a checkout of the repository, regenerate the tool-specific copies with its sync script, re-check for project-specific terms, commit and push, and then refresh the installed copies. When adding a file, register it in the sync script, whose check fails on unregistered files, and add it to the README.
