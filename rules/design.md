# 화면·UX 공통 디자인 원칙

모든 프로젝트의 화면 설계·디자인 검토·UI 문구 작성에 적용한다. 프로젝트 작업에서 사용자가 반복해 지적한 내용을 일반화했다. 프로젝트에 디자인 규칙이 있으면 그 규칙을 먼저 따르고, 이 문서는 프로젝트 규칙이 다루지 않는 부분의 기본값으로 쓴다.

## 화면 위계

- 한 화면의 주요 버튼은 하나다. 같은 모양·같은 무게의 버튼을 나란히 쌓지 않고, 나머지 행동은 보조 버튼·글자 버튼·글자 링크로 낮춘다.
- 단계를 끝내는 주요 버튼은 화면 아래에 고정한다. 특정 내용에 딸린 행동(되돌리기, 바꾸기, 자세히 보기)은 그 내용 바로 옆이나 아래에 둔다.
- 되돌릴 수 있는 행동은 확인 창 없이 바로 실행하고 실행 취소를 준다. 확인 창은 되돌릴 수 없거나 돈·개인정보처럼 무거운 행동에만 쓴다.
- 고른 값이 기록으로 남는 화면은 고르는 즉시 저장하지 않는다. 고른 뒤 확정 버튼으로 남기고, 고르기 전에는 확정 버튼을 비활성으로 둔다. 잘못 고른 값을 바로 바꿀 수 있어야 한다.
- 여러 선택지를 나열할 때는 테두리 없는 글자나 같은 버튼을 쌓지 않는다. 하나의 묶음(테두리 있는 목록) 안에 행(제목 + ›)으로 둔다.
- 강조색은 화면의 주된 행동에 모은다. 주요 버튼 근처의 보조 링크는 강조색·굵은 글자를 쓰지 않고 본문색·보통 굵기 + ›로 낮춘다.
- 행·카드의 덧붙임 정보(최근 사용, 기간, 출처 같은 것)는 제목과 같은 크기·굵기로 이어 쓰지 않는다. 작고 옅은 글자로 제목 오른쪽(› 앞)이나 아래에 둔다.

## 정렬과 배치

- 결과·완료·오류 화면도 다른 화면과 같은 시작 위치(위·왼쪽 정렬)에서 시작한다. 내용을 화면 세로 가운데로 모으지 않는다.
- 한 화면에서 가운데 정렬 글과 왼쪽 정렬 카드·목록을 섞지 않는다.
- 같은 종류의 카드는 이미지 유무와 관계없이 같은 구조로 만들어 글자 시작선을 맞춘다.
- 화면을 검토할 때는 실제 휴대폰 높이(예: 812px)로 본다. 실제보다 긴 캔버스는 빈 곳을 과장해 잘못된 판단을 부른다.

## 상태와 접근성

- 상태를 색만으로 구분하지 않는다. 선택된 칩·행은 테두리나 바탕과 함께 체크를 보인다.
- 대비가 기준(WCAG AA 4.5:1)에 못 미치는 브랜드 색 면 위에는 큰 굵은 글자(16px 이상 굵게)만 올린다. 작은 글자는 그 색 면에 두지 않는다.
- 체크 표시는 이미 된 상태(선택됨, 저장됨)에만 쓴다. 누르기 전 버튼에는 붙이지 않는다.
- 누르는 영역은 44×44px 이상이다. 글자 링크·줄 안의 글자 버튼도 높이 44px을 지킨다.
- 칩·버튼 안 글자가 테두리에 붙지 않게 좌우 여백을 둔다(예: 16px). 글자와 아이콘이 꽉 차 보이면 여백부터 확인한다.
- 화면마다 빈 상태, 불러오는 중, 오류, 결과 없음을 함께 설계하고, 어떤 상태에서도 다음 행동 하나를 보여 준다.
- 기록·평가가 하나도 없을 때 ‘0’을 크게 보이지 않는다. 숫자 칸을 접고 첫 참여를 권하는 짧은 한 줄을 두며, 순위가 있으면 번호 없이 아래에 둔다. 기록이 하나라도 있으면 0도 숫자 그대로 쓴다. 표본이 적을 때 숨길 것은 평균 점수이고, 개수는 그대로 보여도 된다.
- 화면은 이상적인 예시만이 아니라 가장 흔할 실제 상황(예: 출시 첫 주처럼 기록이 거의 없는 상태)으로도 확인한다.
- 빈 입력 칸에는 칸 왼쪽 위에 회색 예시 안내를 두고, 글을 쓰면 사라지게 한다. 빈 줄 때문에 안내가 칸 가운데에 뜨지 않게 한다.
- 시안을 보는 사람에게 하는 조작 안내(예: ‘눌러서 예시를 볼 수 있어요’)를 제품 화면 문구로 두지 않는다. 그런 안내는 화면 밖 설명이나 프레임 이름에만 둔다.

## 이미지가 없을 때

- 이미지가 없다고 자리를 빼지 않는다. 같은 크기의 칸을 두어 정렬을 유지한다.
- 빈 회색 칸만 두지 않는다. 불러오는 중이거나 깨진 이미지처럼 보인다. 칸 가운데에 의미가 분명한 아이콘(예: 음식이면 식기)을 둔다.
- 이모지로 대신하지 않는다. 기기마다 그림이 다르고 맞는 그림이 없는 경우가 많다.
- 불러오는 중(아이콘 없는 칸)과 이미지 없음(아이콘 있는 칸)을 구분한다.

## 다른 서비스로 넘길 때

- 길찾기·예약·주문·결제처럼 다른 앱이 더 잘하거나 공개 연동이 없는 일은 링크로 넘긴다.
- 한 회사 앱 하나만 두지 않는다. 사람마다 쓰는 앱이 다르다. 링크 하나로 앱 고르기 창을 열고 최근에 쓴 앱을 맨 위에 둔다. 앱 로고 대신 이름을 쓴다.
- 같은 무게의 버튼을 앱 수만큼 나열하지 않는다.
- 어떤 앱을 골랐는지 기록해 잘 안 쓰는 선택지는 나중에 줄인다.

## 문구

- 참여를 요청하는 안내는 짧고 따뜻한 한 문장으로, 사용자나 공동체가 얻는 도움을 먼저 쓴다. 조건·주의·안심 문장을 덧붙여 쌓지 않고, 분석 방식은 나열하지 않는다. 필수·선택 여부와 공개 범위만 짧게 붙인다.
- 문구를 제안하기 전에 프로젝트의 기존 문구 규칙과 화면을 먼저 확인하고 그 기준에서 출발한다. 사용자가 쓴 초안이 있으면 대체하지 말고, 걸리는 점 하나를 작은 수정안으로 낸다.
- 한 화면에 굵은 안내 문장을 여러 개 두지 않는다. 안내는 그것이 필요한 입력 바로 위에 한 줄만 둔다.
- 목록·요약의 이름표는 짧게 쓴다. ‘알림 받기(새 소식이 오면)’처럼 괄호 설명을 붙이지 않고, 설명은 입력 화면 한 곳에만 둔다.
- 버튼 이름은 누른 뒤 실제로 일어나는 일과 맞춘다. 지운 뒤 다시 고르는 화면으로 간다면 ‘지우기’가 아니라 ‘바꾸기’다.
- ‘시범’·‘베타’ 같은 운영 상태를 사용자 화면에 쓰지 않는다. 궁금증과 의혹만 생긴다. 신뢰는 내역 공개와 지킬 수 있는 약속(예: 받은 점수는 줄지 않아요)으로 준다.
- 데이터의 쓰임은 실제대로 알린다. 나만 보는 기록을 남에게 도움이 되는 기여라고 하지 않고, 실제로 모아 쓰는 데이터는 숨기지 않고 한 줄로 알린다.
- 고른 값(칩)과 자유 글은 공유 방식을 따로 정한다. 고른 값은 이름 없이 묶어 통계로 쓸 수 있지만, 자유 글은 한 사람의 글이 그대로 가고 개인정보가 섞일 수 있어 사용자가 켤 때만 전하는 편이 기본이다.

## 점수·레벨 같은 보상

- 답이나 이유를 고르는 입력 화면에는 점수를 붙이지 않는다. 점수 때문에 답을 고르게 된다. 받은 점수는 남긴 뒤 결과 화면·알림에서 보여 준다.
- 점수는 실제로 다른 사람이나 서비스에 쓰이는 기여에 준다. 긍정·부정 답에 같은 점수를 준다.
- 공정성을 점검한다. 확인된 행동(증빙 있는 기록)이 확인되지 않은 행동보다 크게 인정받게 하고, 반복으로 쉽게 쌓을 수 있는 행동에는 대상별·하루 상한을 둔다. 기록 자체는 막지 않고 점수만 제한한다.
- 숫자 단위는 받는 맛이 있을 만큼 키우되(+5보다 +50), 돈으로 오해될 크기(+1,000 이상)는 피한다. 1,000 이상은 쉼표를 쓴다.
- 받은 점수는 줄이지 않는다. 기준을 바꿀 때는 더하는 쪽으로만 바꾼다.
- 처음에는 순위표·보상·연속 기록 같은 압박 장치를 넣지 않는다. 첫날 한 번은 레벨이 오르도록 첫 단계를 낮게 둔다.

## 디자인 도구 작업

- 반복되는 UI는 컴포넌트로 만들고, 수정은 원본에서 한 번에 한다. 인스턴스를 떼어내 고치지 않는다.
- 화면마다 값이 달라야 하는 크기(진행 막대 길이 등)는 인스턴스의 크기 덮어쓰기에 기대지 않는다. 변형이나 속성으로 만든다.
- 컴포넌트에 속성을 더하거나 레이어 연결을 바꿀 때 기존 연결(글자 속성 등)을 덮어쓰지 않았는지, 이미 쓰인 화면들의 값이 그대로인지 바로 확인한다. 새 속성은 기본값을 지금 모습으로 두어 기존 화면이 바뀌지 않게 한다.
- 큰 변경 전에는 원본 사본을 보관하고, 고친 뒤에는 반드시 캡처를 직접 보고 확인한다. 복제할 때 감싸는 틀까지 딸려 오지 않았는지, 글자가 잘리거나 겹치지 않았는지 본다.
- 한 흐름을 보여 주는 화면들의 예시 데이터(이름, 날짜, 숫자)는 같은 이야기로 맞추고 합계가 맞는지 확인한다.
