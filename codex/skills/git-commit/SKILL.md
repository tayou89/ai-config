# Commit Workflow

Follow the current user request, applicable project instructions, and Codex permissions. Existing explicit authorization remains valid; do not ask again for the same approved action. These are personal working conventions, not universal language requirements.

Use normal Git commands or the connected GitHub interface. Claude's commit wrapper and PreToolUse hooks are not installed or required by this skill. The checks below are instructions, not an automatic command interceptor.

## Review the Change

1. Inspect the current branch, `git status`, recent commits, and the full intended diff. For a base branch, follow the user's requested branch policy or use an appropriate working branch for implementation work. Do not require an extra branch for an explicitly approved configuration update.
2. Check logic, error handling, concurrent state, secrets, test-only changes, and source/generated-output consistency. Run relevant checks with the installed toolchain. Resolve findings within scope before proceeding.
3. Stage only exact intended paths or hunks. Preserve unrelated staged and unstaged work. Inspect `git diff --cached` and its file list; do not unstage, stash, restore, or overwrite user changes merely to make the tree look clean.
4. Group commits into independently coherent, buildable, revertible topics. Source definitions and their first consumers generally belong together. A version's release manifest, lockfile, changelog, and release documentation form one release commit; unrelated cleanup remains separate.

## Commit Message

Use English with a capitalized type: `Feat`, `Fix`, `Refactor`, `Chore`, or `Merge`. Subject starts with a concrete verb, has no trailing period, and is at most 72 characters (about 50 preferred).

Separate the body by one blank line. Use 3–5 `- ` bullets, at most 8 nonblank body lines, and at most 72 characters per line. Explain purpose and context, especially in the first bullet. Write subject and body for a reader who has not seen the project's own documents, saying why the change was made rather than summarizing the changed document, and leave out internal shorthand (Step N, Phase N, Pattern N, document section numbers such as `0-16`, option or draft letters, session or tool nicknames) and the work's date or author, which Git already records. Do not add generated attribution or Co-Authored-By trailers unless the user explicitly requests them or the repository requires them.

For release preparation, use `Chore: release vX.Y.Z` and bundle the files for that version.

## Authorization and Execution

Commit and push each completed unit of work without asking (user decision, 2026-11-09): the checks in this skill and the repository's pre-commit hook stand where that approval was. Before committing, check on your own: the staged files are exactly the ones you changed, listed by name rather than from `git status` output; no credentials or live-looking tokens; type, lint, and test runs pass when code changed; and the message follows the rules above. For a change of 200 or more lines outside documents and lock files, first get a checklist review of the staged diff from a separate reviewer run and fix what it finds. Stop and ask only when a check fails and cannot be fixed within the task, or when your change cannot be separated from another session's edits in a file. Changes to rules, skills, hooks, and shared settings are the exception: show the change and get the user's review before applying it, then commit and push it without asking again. After pushing, report each commit in one line: short hash, subject, and file count.

Write the exact message to a temporary file and run `git commit --file <message-file>` after verifying the staged scope.

When other sessions work in the same checkout, the default index is shared: their commit can take what you staged, and a stale index after your commit lets their next commit silently revert yours. Stage in a private index, which records file contents but not the commit it was read from: one built before another session's commit would revert that commit. So build it from a recorded base and commit only while HEAD is still that base, comparing again right after the commit. Another session can commit the moment `git commit` returns, so read your commit back from the reflog entry that carries your `GIT_REFLOG_ACTION` mark and your subject (commands a hook runs inherit the mark), not from a second `git rev-parse HEAD`: `base="$(git rev-parse HEAD)" && idx="$(mktemp)" && mark="commit via codex $(od -An -N8 -tx1 /dev/urandom | tr -d ' \n')" && GIT_INDEX_FILE="$idx" git read-tree "$base" && GIT_INDEX_FILE="$idx" git add <paths> && test "$(git rev-parse HEAD)" = "$base" && GIT_REFLOG_ACTION="$mark" GIT_INDEX_FILE="$idx" git commit --file <message-file> && new="$(git log --walk-reflogs --fixed-strings --grep-reflog="$mark: $(head -n 1 <message-file>)" --format=%H HEAD | tail -n 1)" && test -n "$new" && { test "$(git rev-parse "$new^")" = "$base" || { git update-ref -m "undo a commit built on a moved HEAD" HEAD "$(git rev-parse "$new^")" "$new"; false; }; } && git log --oneline -1 "$new"; rm -f "$idx"; git reset -q -- <paths>`. If a `test` fails, another commit landed after the base (the last group also undoes a commit that `git commit` built on it, moving HEAD only while HEAD is still that commit): rebuild from the new HEAD and commit again. If that `update-ref` itself fails, another commit already sits on yours, and if `$new` is empty, the commit cannot be identified: in both cases do not push; check `git log` and tell the user. Write the subject with single spaces, since the reflog collapses runs of whitespace and the search would then find nothing. For a file that also holds another session's uncommitted edits, build its content from `git show "$base":<path>` plus only your change and put it into the private index with `git hash-object -w` and `git update-index --cacheinfo`. Then, as its own command before any push, confirm with `git show --stat <sha>` for the commit the last line printed that it has your subject and only your files; if your changes landed in someone else's commit, report it instead of rewriting pushed history. For an already prepared merge/cherry-pick index, inspect that index rather than re-staging indiscriminately. Follow repository hooks; do not bypass them.

Before amending, inspect recent history and determine whether the previous commit is owned, unpushed, and part of the same topic; amend only such a commit. Obtain authorization for rewriting pushed history. Do not amend others' commits or force-push shared history on your own. If a force push is explicitly authorized, inspect the current remote head and use a lease.

Push once per task, after its last commit, as a command of its own, without asking: the current branch to its own remote (user decision, 2026-11-09). Ask first before a force push, deleting a remote branch or tag, a mirror or tag push, a push to another remote or ref, or any push in a repository that sets `shellGuard.askBeforePush`. Commit straight to the branch a solo repository works on, without a pull request, unless the project's rules say otherwise; when a push there starts deploying, ask before pushing or move the repository to pull requests with required checks. Verify the remote result. Update the associated plan and status records with the actual commit hash and completed scope; do not mark unverified work complete.

Never commit credentials, real `.env` files, unrelated configuration, or temporary test patches. Do not automatically include Claude settings or permission changes.
