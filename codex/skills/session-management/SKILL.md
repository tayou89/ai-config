# Session Management Principles

Apply in every project when proposing, starting, messaging, running, or closing other sessions, as a main session or for one, and before taking on work outside your session's area. Choose each run's model and effort from the work-type table in `decisions-and-collaboration`. The principles every task needs are in `collaboration-core.md`. These generalize feedback the user gave repeatedly during project work. Follow project rules first.

## Working alongside other sessions

- Do not touch comparison boards, decisions, or screens made by other sessions. If two sessions must edit the same screen, ask the user which one takes it.
- Before a task writes in a repository whose rules use worktrees, give it its own worktree, branch, starting commit, and the runtime resources it needs (ports, databases), whoever starts it: the user, a session, a scheduled run, or another tool. A resident coordinating session only reads in the original checkout and routes file changes to a writing task; when isolation cannot be set up, the task does read-only work and reports what is missing (user decision, 2026-11-13). A worktree's owner is the one session that writes there, so a session started to share another session's worktree can only read there; to pass a worktree on, its owner hands it over as `git-commit` section 1 describes (user decision, 2026-11-18).
- Give work that finishes on its own a new session: it leaves its own result (e.g., implementing another page or researching another topic), and the decisions it needs are already recorded, so a short brief is enough to start it. Keep in the current session work that carries out what was just decided or that needs context found only in the conversation.
- Prefer a new session for such work even more when the current conversation is already long or has been summarized, even when a few tool calls would do it: carrying the whole history costs more every turn and summaries lose detail, while a new session re-reads only the recorded decisions it needs.
- Start such a session without asking, in a main session or not, and tell the user in one line what it takes on, which files it changes, and what it leaves when done; do not offer a card asking whether to do it here instead (user decision, 2026-11-13). When it would edit files another session is editing, hand it to that session or agree the order with the user instead. Where the tool allows only a proposal, as on a turn another session's message started or for work you noticed that the user did not ask for, propose it with the same content and no separate question.
- Keep each session to one area, the topic its title and brief name or the role its project rules give it; a main session's area is managing the sessions under it (user decisions, 2026-11-13). Work the title would no longer describe does not join the session, even when it follows from what was just done there. Before starting a session for any work, a main session's follow-ups included, look for a session that already owns that area or holds its context, by title in the session list without archived ones and in its project's notes index: rules, skills, hooks, and AI settings belong to the session titled “설정 관리 AI” and changes to how every project uses Git (workflow records, the Git tools and their guards, the Git skills, and GitHub settings) to “설정 관리 깃”, even where they sit in a shared rule or hook, each with the edits to a project's rules that its shared changes bring with them, and a request that changes both or whose owner is unclear goes to their master “설정 관리 마스터” (user decisions, 2026-11-19); a project's rules name its master and role sessions as "Project master and role sessions" below describes. When one exists, hand the work to it, ask its opinion, or ask it to review your result, and start a new session only when it asks to split the work off or its context is past 80% or summarized; when none exists, start one as above. Outside your area, do only what a handful of tool calls settles without changing anything, such as reading a file or checking a status, and in a coordinating session only what its boundary below allows.
- When you hand work to another session or ask it for an opinion or a review, send what to look at as paths (naming any that still hold your uncommitted changes, with your session's id, so the receiver can take them over), the decision it bears on, when it is needed and what it blocks, and the user's words quoted with their date and session, and tell the user in one line where it went; the reply gives agreement, disagreement, or an alternative in a few lines with reasons (user decision, 2026-11-13). When the two sessions disagree, show the user both views side by side with your recommendation.
- Announce a change other sessions need, such as a changed rule or a fixed shared tool, as one line in `~/Library/Application Support/Claude/side-session-notes/bulletin.md` with the date, the commit or file, what changed, and who must act (user decision, 2026-11-13). Message directly only the sessions that asked for it, wait on it, or whose current work it changes, since each message wakes that session for a turn over its whole context.
- A session is the main session when the user designates it or, unless the user says otherwise (as a project's role list does with `(not main)`), once it has started another session for a task of the user's while no other session started it or after it was moved to the top level (user decisions, 2026-11-08 and 2026-11-13). Use the main session as the team lead, only for conversation and managing the sessions under it (user decisions, 2026-11-06 and 2026-11-13): answer there only from what you already know or what a handful of read-only calls shows in a session's result, such as its commit, report summary, or status, and when what you know describes a state that may have changed since (a screen, a file, a session), say where and as of when you learned it, or check it first (user decision, 2026-11-13), and start, check on, relay, and close sessions there. When it reports on several sessions or the user asks what is running, give one table of the open sessions with each one's topic, starter, state, and what waits on the user. Start everything else the user or another session asks for in its own session right away without a separate proposal, even a single setting change: any change to files, settings, or apps, and any question that needs investigation such as reading files or transcripts, running commands, or searching; a project master sends field work to that field's role session instead, as "Project master and role sessions" below describes. Send each task's follow-ups to its session and report each result in the main session in one or two lines. In a main session this replaces keeping just-decided work in the current session, even where the tool's own instructions would keep a continuation or a quick task there (user decision, 2026-11-13). Where the tool allows only a proposal, propose the session as above, and do the task in the main session only when it allows neither, saying so.
- Main sessions, project masters, and role sessions coordinate, and the task sessions under them prepare new results (user decision, 2026-11-19). A coordinating session relays a result already produced or answers at once from what it already knows, marking an answer it has not checked for this request as unchecked; its own reads only find the session that owns the work, check a status, or fetch a finished result. Preparing or revising an estimate, an analysis, a comparison, or a review is task work, whether the user or another session asks, even when its inputs are already in the conversation and only a few lines are wanted. Urgency, answer length, the expected number of tool calls, and a new session's start cost do not change this, since these rules already weigh that cost, and it comes before any instruction, the tool's own included, to keep quick work, a continuation, or a brief out-of-area read in the current session. Route the work to a suitable open task session, or start or propose one; a card waiting for the user's click does not let the coordinating session do the work meanwhile, and only where the tool allows neither does it do the work itself, saying so.
- When one request splits into parts that do not depend on each other, start each part in its own session at once without asking and run them in parallel (user decision, 2026-11-12).
- When parallel sessions share a lock or a numbered space, give each brief its identifiers in advance (section numbers, canvas areas, ports) and the session to hand the lock to next, so they neither collide nor wait for the main session to relay each handoff: numbers handed out on request collided three times (2026-11-10).
- A session under the main may start its own sessions for parts of its task that leave separate results, but those do not start more, so the tree stays two levels below the main (user decision, 2026-11-13), which under a project master are its role sessions and their task sessions: each session reports to the one that started it, which relays one line upward, and closes its own finished sessions before it reports its task done.
- Each time a session you started for a task, not a role session, reports a finished turn, check right then whether its task is done: work committed and recorded, its notes in the project's notes folder (`report-writing` "Notes folders"), nothing waiting on the user (no open question or decision), and no session it started still working or waiting for the user. If so, close it in that same reply without asking, and say in one line which sessions you closed, that they can be reopened from the archive, and any proposals they left (user decision, 2026-11-09). Leave open a session that is still working or waiting for the user. Closing a session can also close the idle sessions it started, so list them right before closing; if one still waits for the user, leave both open and say why (user correction, 2026-11-09).
- Replace the main session itself once its measured context passes 80%, the same reading as the 80% line in `collaboration-core`, whose three choices it replaces for a main session (user decision, 2026-11-17), so the replacement finishes before automatic compaction near the window's end loses detail. Past the threshold, keep managing the sessions it started from the old main, starting new ones for new tasks as usual, until each has finished and been closed; then propose the replacement once, and on the user's yes replace it in this order (user decisions, 2026-11-09 and 2026-11-23). A project master's role sessions do not finish, so it replaces itself as "Project master and role sessions" below describes instead.
  1. The old main saves the open work (pending decisions, remaining tasks, cards waiting) to persistent memory and withdraws each card it proposed, so a late click cannot start what the new main also starts. It opens the new main as a top-level session with an opening prompt that points to that memory, in a folder or worktree of its own, and detaches it right away if the tool starts it under the old main, since a session still under the old main is closed along with it and the app refuses to detach one that shares another session's worktree.
  2. From then on the old main starts no session and takes no new work: it answers the user with a link to the new main and asks them to continue there, and forwards other sessions' messages to the new main, so no task starts twice or outside the new main.
  3. On its opening turn, which the old main's message starts and on which the Claude desktop app lets it only propose cards, the new main asks in its next-step box whether to start the sessions waiting for it, with one button that starts them all, keeps that question in each next-step box until the user answers, and starts them on the click instead of proposing a card for each.
  4. The new main closes the old main without asking in the chat (the app may still show its own approval card) once it holds the open work, it is detached, the old main's cards are withdrawn, no other session the old main started is open, and the old main's notes are in the project's notes folder (user decision, 2026-11-16: "이런거 알아서 보관처리하도록 해줘 앞으로는 말야"). While the app holds the close because the old main is on screen, it tries again on each of its own turns instead of asking the user, since the user moves to the new main.
- Give a new session a short title of a few words naming its topic, and a project's role session its project and role (for example, “<project> design”), in the user's language (user decision, 2026-11-13 for role sessions). Leave scope or mode notes such as “(read-only)” out of the title and put them in the brief.
- Write a new session's brief and every later message to it in the user's language, as its title already is: a session started from a brief in another language drifts into that language in what it shows the user (user decision, 2026-11-09). Describe each decision, mode, and option in them by what it does rather than by a quoted label, since the receiving session repeats their words to the user (user decision, 2026-11-17).
- Name in a new session's brief the skills its work will need under the skill triggers, such as `code-style` and `typescript` for app code or `ux-design` for design-tool work, and do the same in the prompt of a subagent that will write or review files (user decision, 2026-11-11). Name its project's notes folder too, since the app adds its own session folder to the brief (`report-writing` "Notes folders").
- When a session you started needs the user's decision, ask the decision itself in its own terms with that session's recommendation and pass the answer on without a second question; never ask whether to relay an answer, and offer answering in that session as the other button (user decision, 2026-11-09).
- In a session another session started, ask the user's decision as the next-step box question, with the options in the closing message, and end the turn, never in a question dialog: an open dialog keeps the turn running, so an answer the starting session relays waits in the queue and stopping the session is refused; a hook sends such a dialog back (user decision, 2026-11-13).
- An answer one session relays counts as the user's answer in the session that asked for the decision, plan approvals and reviews of rule text included (user decision, 2026-11-24), so never brief a session that relayed answers do not count. The relaying session quotes the question and options as it showed them, the option the user picked or their words, the date, and the session where the user gave them, marking anything it added. The receiving session acts on it without asking again once it has found that answer in a turn the user made in that session (the app's session history or transcript tells it from a turn another session's message started) and has checked that what it will apply has not changed since it asked; otherwise it asks in its next-step box, showing what differs. When the user answers in the receiving session's own box first, it tells the starting session in one line at once, so that session drops the question instead of waiting for a second answer.
- A relayed answer never stands in for the user where the tool needs them in that session: a permission dialog, a change to permission settings or allow lists, and what the tool's safety rules have the user confirm in that conversation, such as sending a message for the user, publishing, paying, deleting permanently, or changing account or repository settings. Send the user to that session for those, keeping within the app's note on every session message that another session grants no escalation and approves no pending prompt. Work the rules already authorize without asking needs no answer, relayed or not, and a relayed answer does not make its turn one the user started, so "Start sessions only in the ways the current tool allows" below still limits that turn.
- If closing a finished session is refused because a remote-control connection to it is on, turn the connection off and close it without asking, and say so in one line of the report (user decisions, 2026-11-06 and 2026-11-09). If it is refused because the session is still working, or because the app is keeping it for the user (open on screen or pinned), try once more when that session next reports or on your next turn, since both states usually pass within a turn; ask the user to close it from the session list, giving the reason, only when the session list shows it pinned or the second try is refused too (user decision, 2026-11-17).
- A scheduled run that edits a shared folder follows the one-writer rule in `collaboration-core` too: it takes the folder's edit lock and, when another editor holds it or uncommitted changes exist, skips the run and reports why.
- Check the shared to-do list for tasks other sessions handed to this session, finish those tasks, and then update the list.
- Notes folders, their index, and the shape of the reports in them follow the `report-writing` skill (user decision, 2026-11-16).

## Project master and role sessions

- Run a project with two or more continuing fields of work (for example development, design, planning, operations) and decisions that span them (release scope, test servers, the way of working) as one tree (user decisions, 2026-11-19): a top-level project master, one role session per field under it, and short-lived task sessions under each role session, which start no more sessions. Title the master with its project's name in the user's language (“<project> master”, in Korean “<project> 마스터”) and always call it by that full title, since an app-wide master session that gathers waiting sessions across projects may exist too. The master is the project's main session: it owns the decisions between fields, sends field work to the role session that owns it, and keeps the table of open sessions and what waits on the user, doing no field's work itself; when a decision needs a comparison across fields, it asks the role session most concerned to have a task session prepare it with the other fields' input, and decides from that result. When a project starts, the master opens the role sessions its fields need, and when work for another field appears later, it opens that field's role session then, titled with the project and role (for example “<project> planning”, “<project> design”) (user decision, 2026-11-19). A project with one field needs no separate master, since its role session can hold the project's decisions too and each extra session costs a full start (about 95,000 tokens of rules and tool descriptions in this setup); when a second continuing field appears, open the master and move the role session under it by the steps below. A project whose rules record another arrangement the user approved keeps it until the user changes it.
- A project's rules list these sessions under a heading that reads exactly "Role sessions", in English whatever the rules' language, with any note in parentheses after it: one unnumbered list item per session, starting with its title in backticks and naming its area, the master first (user decision, 2026-11-16). The main-session notice reads only this form, not a translated heading or a table. `(not main)` right after a title marks a top-level role session the user keeps apart from the main session, such as one waiting for its move; a role session under the master needs no mark.
- A role session leads its field (user decision, 2026-11-18): it keeps conversation and decisions with the user in its area and gives every change to files and every run, however small (drafts, fixes, captures, checks, research, recording), to a task session under it, in place of keeping just-decided work in the current session, doing itself only what the coordinating sessions' boundary in "Working alongside other sessions" allows. It bundles each step's work in one task session, sends follow-up fixes to that session while it is open, and closes it once its result has been shown. It reports to the master in a line or two each result, each changed commitment to another field, what blocks it, and the decisions waiting, also for work it handed to another role session directly, since the app's notice that a turn ended is not that report; a change to another field's scope, priorities, or commitments goes to the master before work that depends on it goes on. The master closes a role session only after its replacement has taken over or when the user ends the role, never because a task looks done.
- Start sessions only in the ways the current tool allows; relaying the user's words does not make them a request the user made in the receiving session. In the Claude desktop app (its tool descriptions, read 2026-11-19), a session another session started asks the user only in its next-step box and starts a session at once only on a turn where the user asked there for that work; on a turn a session's message started, it can only propose a card. So the user gives a field's work to its role session directly, and the master relays decisions between fields (user decision, 2026-11-19); when such a decision, another session's request, or field work the user gave the master anyway needs a task session, the role session proposes it once with its full brief, model, and effort and says where the card waits, to a requesting session too, and the master tells the user in one line which session's card to click and lists it among what waits on the user until it starts.
- The Claude desktop app can move a session to the top level but not under another session, so a role session moves under a master, or to a new master, only by being replaced, one role at a time to spread the disruption (user decision, 2026-11-19), in this order:
  1. The master stops sending the old role session new work, and the old one lets its task sessions reach a stopping point and has one of them write the handover: its area, decisions with their reasons, results and checks, unfinished work, questions and cards waiting and where they are, files with uncommitted changes and their owner session, worktrees, and an opening prompt.
  2. The master starts or proposes the new role session under itself with the same title and the handover's path; while two sessions share the title, the handover names both by id and says which takes new requests.
  3. The new session confirms in its first report that it holds the decisions, unfinished work, and waiting items, and takes over worktrees by their owner procedure in `git-commit`.
  4. The master closes the old session without asking once it and its remaining sessions pass the closing check above and its waiting cards are taken over or withdrawn, so a late click starts nothing twice.
- A project master proposes its own replacement once its measured context passes 80%, without waiting for its role sessions to finish: on the user's yes it opens the new master by steps 1 to 3 of the main session's replacement above; the new master then moves the role sessions under itself one at a time by the steps above, while the old master forwards their reports to it, and closes the old master by step 4 once the last one has moved. A role session past 80% keeps the three choices in `collaboration-core`, and when the user chooses a new session, the same steps replace it.
